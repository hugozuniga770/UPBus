# Glosario — UPBus

Busca la sigla, lee su significado y sigue.

## Siglas de los documentos

| Sigla | Significa | Ejemplo |
|---|---|---|
| RF | Requisito funcional: algo que la app debe hacer | RF-07, «Voy a subir» |
| RNF | Requisito no funcional: cómo debe hacerlo (rapidez, seguridad, privacidad) | RNF-01, ubicación cada 10 s |
| RN | Regla del negocio: una norma del servicio que la app debe respetar | RN-03, mínimo 15 estudiantes |
| HU | Historia de usuario: una necesidad contada desde quien la usa | HU-04, ver mi bus en vivo |
| CA | Criterio de aceptación: condición que debe cumplirse para dar por buena una historia | HU04-CA2 |
| D-xx | Decisión técnica o de producto ya tomada | D-02, SQLite |
| P-xx | Pregunta abierta que el equipo debe responder | P-02, cómo se hace el tiempo real |
| C-xx | Cambio registrado a algo ya acordado | C-01 |

## Marcas

| Marca | Significa |
|---|---|
| [ACUERDO] | Lo decidió el equipo o sale de la guía oficial de buses de la UPB |
| [PROPUESTA] | Lo propuso el Product Owner y el equipo todavía no lo confirmó |
| [PENDIENTE] | Depende de una pregunta abierta (P-xx) |

## Términos

| Término | Significa |
|---|---|
| Padrón simulado | Lista de estudiantes que imita la base de la UPB; se usa para validar el registro |
| MoSCoW | Forma de priorizar: Must (debe estar), Should (debería), Could (podría), Won't (no por ahora) |
| MVP | Producto mínimo viable: la primera versión que ya resuelve el problema principal |
| Product Backlog | Lista ordenada de todo lo que se quiere construir |
| Sprint | Ciclo corto de trabajo que termina con una versión que funciona |
| Incremento | Lo que se terminó en un sprint y cumple la Definition of Done |
| Definition of Done | Lista de condiciones para decir que una historia está terminada |
| Tiempo real | Que la información (por ejemplo, la ubicación del bus) se actualice en segundos, sin recargar la página |
